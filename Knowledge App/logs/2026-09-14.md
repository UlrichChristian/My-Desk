## 16:40 — Financial app schema refactor (Deploy A)

Rebuilt `fin_db` on a reference spine anchored on the EA account `oid`, and
built the HRIS / payroll integration overview on top of it. Schema is in
`Financial Management App/schema.dbml` (paste into dbdiagram.io).

**What replaced what.** 15 new tables: `accounts`, `clients` + `client_keys`,
`advisors`, `consulting_houses`, `carriers`, `account_policies`,
`account_period_metrics`, `income_accounts`, `products`, `revenue_lines`,
`revenue_imports`, `ingest_corrections`, `integration_vendors`,
`account_integrations`. The legacy tables (`fact_revenue`, `account_snapshot`,
`dim_*`, `import_batch`, `client_mapping_override`) are still created and still
hold their data — they are the rollback and get dropped in a later change.

**Parity is exact.** 85,847 revenue rows, 38 unresolved (both unchanged), all 13
periods tie on row count *and* amount, and all 491 clients tie to the cent.
2026-08 total is 432,925.39 in the app, same as before. `tests/test_migration_parity.py`
is a merge gate that re-runs this against the preserved source files.
97 tests pass.

**Two findings from the data.**

1. *The August WF Steel row is a duplicate.* The source drilldown carries a 7th
   deferred-revenue JE dated 2026-08 reusing reference `WFSteel_Deferred_#1`,
   with February's amount ($1,632), February's description and — the giveaway —
   February's cumulative Balance (618,111.23). A running balance cannot repeat.
   Christian confirmed it is a copied line; it is now excluded by an
   `ingest_corrections` rule with the reasoning recorded. **Still to fix at
   source in QuickBooks.**

2. *The Aug-2025 manual qty/rate repairs are gone.* `scripts/extract_manual_corrections.py`
   diffs the stored fact against a fresh parse of the preserved file and found
   zero surviving edits — the 2026-09-02 full re-import wiped them, exactly as
   the 2026-07-29 log warned would happen. Not recoverable from anything on
   disk. Christian will re-enter them through the corrections table, which now
   survives re-import. (First pass of that diff produced ~40 false positives
   because the join key is not unique; it compares multisets per key group now.)

**The (13)/(14)/(15) suffix is the HST rate, not a pay frequency** — Christian
corrected an earlier reading. 13 Ontario, 14 Nova Scotia, 15 NB/NL/PEI, bare for
GST-only provinces. 15 does not identify one province so province is not
inferred. `products` splits `benefit_code` from `hst_rate`, which means "Extended
Health revenue nationally" is answerable for the first time — it was previously
four unrelated strings (`Admin-EH` + three suffixed variants, 7,888 rows).

**Other things now captured** that were parsed and discarded: 47 carriers and
5,170 policies (parsed out of `policies`, and the join key to the Reconciliation
App), GL reference codes, effective/first-billed dates, benefit + package type,
and consulting house — which was computed on every import and had no column to
land in, so it was never reportable.

**Deliberately not captured:** `divisionCodes` (one account carries 1,175),
`classCodes`, `blockNames`. No consumer.

**Deploy B (not done):** delete pre-2026-07 `account_period_metrics` rows so
historical Revenue/Premium goes blank instead of being computed against today's
premium. Held back deliberately — it blanks a column across twelve months, which
would have camouflaged any attribution regression in this deploy. `load_import(metrics_mode=...)`
takes `all_periods` (current, reproduces old behaviour) or `latest` (honest).

**Also still open:** drop the legacy tables after a month of real use; the
reference review screens for `products`/`income_accounts` rows auto-registered
as `status='review'`; Process Street mirror for the HRIS import.
