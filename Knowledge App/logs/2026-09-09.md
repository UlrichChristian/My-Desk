## 13:40 — Financial app schema audit ahead of HRIS/payroll integration overview

Reviewed `fin_db` before extending it. Findings:

**Nothing in the revenue store is stable.**
- `fact_revenue` is replace-by-period: `load_import()` deletes every period the
  new drilldown covers, then reinserts. Christian re-uploads full history each
  time, so import 8 (2026-09-02) owns all 13 periods — imports 1-7 have zero
  surviving fact rows.
- Worse: `enrich()` joins *every* row, whatever its period, to *today's*
  accounts CSV. Verified — 1,073 of 1,073 oids have byte-identical
  premium/lives in all 13 periods, zero variance. So Revenue/Premium for
  2025-08 is computed against September 2026 premium. `advisor_key` has the
  same problem. Only `amount`, `quantity`, `rate` (straight from the drilldown)
  are period-correct.

**The dim tables are dead.** `dim_client`, `dim_advisor`, `dim_product`,
`dim_income_account` are declared in `_SCHEMA` and have 0 rows. Nothing writes
them (the `load_import()` docstring claims an upsert that does not exist) and
nothing reads them. Attributes live denormalized as free text on `fact_revenue`.

**`account_snapshot` is write-only.** 11,675 rows, 8 vintages accumulated
correctly — but `client_key` is hardcoded NULL on insert and no code ever
queries the table. It is the only historical record we have and it is unused.

**Two things do survive an import:** `client_mapping_override` (re-applied on
each `enrich()` — this is the pattern to copy for any new reference table) and
`account_snapshot`.

**Nothing generates a stored overview.** `report_from_db()` → `_period_frame()`
(raw SELECT on `fact_revenue`) → `_rollup()` (groupby `client_key`) computes the
Biggest Clients table at request time. No materialized view, no cache.

**For the HRIS/payroll feature:** the source systems carry no integration data.
The accounts API returns 32 columns — `memberUpdatesType`, `ssoEnabled`,
`benefitPackageType` are the closest and none of them name a vendor. So
ADP / SAP / Dayforce / Workday etc. is net-new, hand-maintained reference data.
It must key on `oid` (stable) not `client_key` (derived from GROUP ID on every
import, drifts silently), and must live in tables `load_import()` never touches.

Design proposed: `dim_account` (oid spine), real `dim_client`,
`dim_integration_system` (vendor catalogue), `account_integration` (the fact,
SCD-lite with effective_from/to). Not yet built — awaiting Christian's call on
client-level vs account-level grain.
