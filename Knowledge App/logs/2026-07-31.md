# 2026-07-31

## 09:11 — Reconciliation App v3: evaluated EN 16931 / ZUGFeRD / Factur-X for import format

**Context:** Reviewed App v3 (CMRRA Reconciliation App) as a prototype. App converts both
carrier invoices and EA (CSIP) statements into one bespoke JSON shape (`CarrierInvoice`)
before importing, today via 15 hand-written parsers. Question raised: should we adopt the
European standard that embeds structured XML inside PDF invoices?

**The standard:** ZUGFeRD (DE) / Factur-X (FR) — the same Franco-German hybrid format. A
PDF/A-3 with **EN 16931** XML embedded (UN/CEFACT CII syntax). EU-mandated (Directive
2014/55). The appeal: structured data rides inside the human-readable PDF → no parsing/OCR.

**Decision: NOT adopting the format. Consciously deferred.** Two hard blockers:
1. **No counterparty will send it** — our carriers are Canadian (Canada Life/GWL, Manulife,
   Sunlife, Empire, Desjardins, Greenshield, Equitable, NHC); EN 16931 is an EU mandate with
   no Canadian pull. The one thing that would kill the 15 parsers (structured data in the
   PDF) is exactly what we can't get.
2. **Our documents aren't commercial invoices** — they're account-statements + a
   dual-statement reconciliation (opening/closing balances, required float, balance-forward,
   claims paid, fee-factor splits, HCSA/ASO/PWA, carrier vs EA side-by-side). EN 16931 has no
   home for running balances or reconciliation, so it's a poor fit and custom extensions
   would throw away the interoperability that was the only reason to adopt a standard.

**What IS worth doing (someday, not now — driver was future-proofing + interoperability):**
- Borrow EN 16931's **rigor**, not its wire format: give the canonical JSON a real versioned
  machine-readable schema (today there's none — just dataclasses + imperative `validate()`),
  add explicit **currency** (implicit CAD floats today), and name fields the EN 16931 way
  where they map (currency BT-5, parties BG-4/BG-7, line items BG-25, tax breakdown BG-23,
  totals BG-22). Keep reconciliation fields as a labeled EA extension block.
- Keep the "structured data inside the human-readable doc" trick as a North Star for
  documents **EA itself generates** (where we control output), if a mandate/partner appears.

**Status:** Understanding only — no build requested. Full write-up parked in plan file
`a-question-we-are-velvet-codd.md`. Revisit if EA touches the EU market or Canada moves on
e-invoicing mandates.
